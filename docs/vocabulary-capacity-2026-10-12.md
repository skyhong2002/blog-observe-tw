## 排名規則

原始 tag 詞池完整保留。以過去 365 天 verified 部落格文章為分母，詞在標題或正文出現的文件比例超過 **2%** 時，排行榜只計標題命中；原始正文證據仍保留，詞彙頁顯示 `high-document-frequency-title-only` 原因。這是可在 `FREQUENCY_POLICY` 調整並帶版本的規則，不是另外造通用詞黑名單。小標與原生分類不混入本次 title-only 權重。

基準共 4,118 篇，其中 4,103 篇已完整比對，15 篇受既有內容上限限制。正例比例以全部文章為分母，因此不足覆蓋不會誤放大比例。詞庫 UI 同時顯示覆蓋，不能宣稱未索引文章都不含該詞。

升溫倍率＝近期文章比例 ÷ 365 天基準比例；高頻詞兩邊皆採標題命中。基準含近期窗口，這是相對比例，並非獨立前一期的成長率。無基準時為 null；單站頁不拿全站分母算倍率。排序仍採標題權重 2、正文 1、同站貢獻逐篇減半，沒有偷偷改為倍率排序。

「選擇／比較／需要／建議／價格／分享／人氣／自由／特色」均已進高頻規則，但合法標題命中仍可上榜；其他低於門檻的通用詞可能仍出現，不另刪詞。

## 完整詞池與活躍比對集

- 完整上游快照採分頁、每批寫入資料庫，逐頁保留 hash／receipt／cursor，可中斷續跑；不把 250,000＋詞整份載入 RAM。安全閥為 2,000,000 詞、2 GiB 暫存（包含驗證 receipt），超過會保留上一版並回報，不把截斷結果發佈成完整。
- 接受 `noise`、`noEqual`、`recentArticleCount`，保留 articleCount、最近發表時間與上游來源。沒有進活躍集的詞仍可查原因。
- 活躍条件：非 noise／noEqual、長度至少 2；且 articleCount ≥3 或最近 180 天出現。符合者依 articleCount 降冪、穩定 ID 決勝排序，再受記憶體預算限制。
- 比對索引上限 50,000 詞、150,000 code points、估算 96 MiB，任一先達即停止納入；其餘記為 memory-budget，低頻記為 low-frequency。不是刪除原始詞。
- 同一實測窗口原始詞 21,573，活躍 21,086，估算 68.55 MiB；完整上游池尚未部署通知，無法假報其實際活躍總數。
- 300,000 詞合成串流測試：三種詞形各納入 39,321／16,666／1,229 詞，估算 96.00／89.52／74.41 MiB；實測保留 heap 38.37／14.55／1.07 MiB，建構增量 57.46／57.67／27.09 MiB。RSS 包含 Node 與連續測試（最高約 323 MiB），不等同 trie 自身預算。

## 更新與保留

上游完整快照與 changes 正式契約尚未收到部署通知，正式環境仍用 observed-article-window，明確標示不等於完整池。窗口同步改為每 15 分鐘、最近 24 小時資料快取加 1 小時重疊增量，每日最多 600 個上游 HTTP 請求（含 retry），單一並行；loopback 間隔至少 500ms，公開 fallback 至少 1100ms，service token 與 Retry-After 規則維持。初次落後補齊／上游退避或額度不足時可能延後，不保證失敗時仍即時。

新世代沿用仍有效文章比對、舊世代不覆寫；新活躍詞出現後，最近 48 小時文章標記補比對，worker 每 10 分鐘處理有限批次，完成後刷新頻率基準。更舊文章持續依正常排程處理，沒有聲稱立即重算全部歷史。

本機窗口世代保留最近 32 份，加上 current、未完成工作／父世代、完整匯入 staging、legacy/v2 回滾索引引用與明確 pinned 世代。GC 每批 500 列、每輪最多 250,000 列／合作式 10 秒，超額保留 backlog。若 published＋retiring 超過 64，新建暫緩、既有工作可續跑；retiring 不可復活。完整上游池不被這個窗口 GC 回收。

完整匯入目前只到驗證完成、政策準備好的 READY staging，尚不切換正式指標；tag 宣布 full／changes 上線後才接契約並啟用每日對帳與 10 分鐘 changes，不能把未上線 endpoint 當可用。

## 驗證與回滾

Migration 0014–0017 皆 additive；v3 比對、詞與索引獨立，上一版 v2 留存。部署前備份正式 DB，先準備新 v3 與基準再切服務。若切換後新版發佈了窗口，回滾必須同時恢復切換前 topic_current 指標與舊三服務版本，不能只換二進位。

20 個隔離 SQL suites（含原子預算、分頁／hash續跑、世代複製、頻率、retention、索引回滾）、565 個單元測試、前端測試與型別检查通過。前端由 Opus 實作；Codex 交叉審查整合。Opus 建議採納：shadow v3、複製而非搬移舊索引、頻率刷新、retention 與實測記憶體；未採納「新詞一律只計標題」，因會阻擋新興話題，改為未知基準明示、補比對後刷新。上游 receipt checksum 依 JSON.stringify(entries) 契約核對，未採錯誤的 HTTP 空白字節 hash 假設。
