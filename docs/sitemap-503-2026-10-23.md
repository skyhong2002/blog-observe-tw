# Sitemap 503 修復交接（GSC-20261023）

分工：Claude（本 repo）負責程式修復與部署；Codex 負責 Google Search Console 提交與 Google 側驗證。本文件不操作 GSC。

## 狀態

- 正式：gen99 green `fd8b90dbe79eaf5b424c6525714b9b545e32a300`（2026-10-23 17:38 CST switch）。回滾目標：blue `5c46e9cb3d95bfa0638effc85f81acc2a4ea869c`（gen98，已停止但 release 保留）。
- 程式：`app/src/seo/sitemap-entries.ts`、`app/src/seo/routes.ts`；規則見 [seo.md](seo.md#sitemap-專用精簡讀取2026-10-23)。

## 根因

`/sitemap.xml` 與每份子檔都先 `getIndexablePages(blog)` 與 `getIndexablePages(topic)` 全量，blog 子檔也等 topic：

- blog 經 90 天 topic projection：正式 DB 實測 14.9 秒。
- history 讀取開啟時 topic 走 `cumulativeTopics`：220 萬列 `topic_article_evidence` LEFT JOIN 8.3 GB 的 `content_post_bodies`／`relation_observations` 做全歷史聚合；正式 DB 以 `max_statement_time=280` 實測，280 秒時被中斷。
- edge 等上游標頭 30 秒後回 503 `Retry-After: 2`。

## 修復

- blog：只讀 route × verified blogs 與 posts 的 MAX 有效日期，不讀話題。
- topic：成員條件與舊版相同，只拿掉只用來算 fresh／title_hit 的正文 JOIN；共用 `historyPublicEvidenceSql`。
- topic 子檔依 SHA-256 ID 值域切分，每 1,000 個 topic route 一份，目前 50 份；每份只查自己範圍。index 只需 route 的 PK COUNT，以及「最新公開文章」往回找出的話題 lastmod。
- 不跨請求快取、不延長 timeout、不改公開／私人邊界、不刪歷史。

## 驗證（2026-10-23）

### A. 正式通過證據

- 單元：`npx vitest run app/src/seo app/src/topics` 全過（高負載時 `snapshot-full-caller` 偶發超過 5 秒預設 timeout，單獨重跑通過，與本次無關）。
- Integration（一次性 MariaDB 11.4，`--suite sitemap`）：indexability、topic-history-read 通過；新斷言涵蓋新舊同集合、revoked／noise／merged 排除、來源改非 verified 與證據 revoked 後下一次讀取立即消失、範圍下界含上界不含。拿掉公開證據條件的 mutation 會讓測試失敗。
- 正式 DB 唯讀對照：blogs 舊 478 = 新 478，順序相同；topics 參照（舊 pipeline 去掉正文 JOIN、分批，接未修改的 `getPublicPages`）30,499 = 新 30,499，雙向差集為空、無重複。45 筆 lastmod 不同，都是兩次讀取之間新寫入的證據（參照較新）。
- switch 前在 green gateway 18175 取全部：index 1.83 秒、52 份子檔 200、30,982 URL 不重複；switch 後經正式網域（Cloudflare DYNAMIC、`private, no-store`）取得的 URL 集合與它完全相同。
- 正式網域 `python3 tools/seo/verify.py` 第二次 exit 0（17:5x）：52 份子檔、30,995 URL，156 個首／中／尾抽樣頁皆 200、自指 canonical、無 noindex；單檔最大 661 URL、81 KB，index 6.38 秒，子檔最慢 10.15 秒。另以重試腳本獨立抽查同樣 156 頁：156 OK、0 失敗、未觸發重試。
- 穩定性（正式網域）：18:06 起 root 與 `topics-27.xml` 每 10 秒各 6 次，12/12 為 200 且 XML 可解析，root 12.2 秒（冷讀）後 0.86–3.3 秒，`topics-27.xml` 1.1–2.2 秒；18:09 起 `blogs.xml` 3 次皆 200、478 URL，1.15–2.57 秒。switch（17:38）後 edge／gateway 日誌沒有任何 sitemap 503、`topic_cache_busy` 或 sitemap 錯誤。
- Codex 匿名補查（Google 側另報）：root 200 約 3 秒、`topics.xml` 200 約 4.9 秒；GSC：index 已 processed successfully，直接送的 `topics.xml` Success、發現 604 頁（尚非收錄）。

### B. 初次 metadata 逾時（不是 sitemap）

- 第一次跑 `verify.py`（17:39 起，switch 後 1 分鐘內）在抽樣深頁中斷：web 回 500，因為 web 呼叫 gateway 話題頁 metadata `/api/pages/topics/火車站` 時逾時（web 日誌 17:40:11 `PublicGatewayError … (network)`／TimeoutError）。
- 同類逾時在 switch 後還有 17:45:59 `美術館`、18:05:16 `條件`（後者同時有 edge `ui origin unavailable`／Headers Timeout，是話題 HTML 頁，不是 sitemap）。事後直接打 gateway，`火車站` 1.69 秒、`美術館` 1.04 秒。
- 這條是既有的單頁 `getPageIndexability` → `cumulativeTopics`（scoped，仍帶正文 JOIN）路徑，本次未改；發生在主機 load 約 20–30、swap 約 18 GB 時。另外首頁 `home.mentions` 也有 4 次 statement-timeout（已降級回應，既有行為）。

### C. 連線重置（未證明原因）

- 17:52 第一次跑獨立抽樣腳本時，經正式網域讀某份 sitemap 子檔的內容到一半，出現 `ConnectionResetError [Errno 104]`。edge／gateway 沒有對應錯誤紀錄，無法確認是 Cloudflare、網路還是 origin。立即重跑（加一次重試）156 頁全過，且沒有觸發重試。
- Codex 回報一次 `blogs.xml` 在其客戶端 12 秒 timeout，未證明是 503；日誌裡同期沒有 sitemap 錯誤。`blogs.xml` 主要成本是 posts 的 MAX 日期全表掃描，在本機冷讀實測 9.7–15 秒、熱讀 0.14 秒（已在 buffer pool 時），所以冷讀時可能超過 12 秒，但仍在 edge 的 30 秒內；之後 3 次 1.15–2.57 秒。

## 有效 Sitemap（Codex 提交用）

只需提交 `https://blog.observe.tw/sitemap.xml`（index）。子檔：

- `https://blog.observe.tw/sitemaps/pages.xml`：5
- `https://blog.observe.tw/sitemaps/blogs.xml`：478
- `https://blog.observe.tw/sitemaps/topics.xml`、`https://blog.observe.tw/sitemaps/topics-2.xml` … `https://blog.observe.tw/sitemaps/topics-50.xml`：合計 30,512（每份 563–661）

數量會隨收錄而變。topic route 數跨過 1,000 的倍數時份數會變（目前 49,4xx routes → 50 份），各話題所屬檔案也會跟著移動。舊格式的 `topics-2.xml` 等網址仍有效，只是內容依新切法。

## 公開／私人邊界

列入：verified 部落格的公開頁；至少一篇公開歷史文章（confirmed／pending 證據、verified 來源、非未來文章）且 active／pending、非雜訊、無現行排除的話題。不列入：私人閱讀清單、登入／管理／搜尋／API 資料、非 verified 來源、revoked／merged／雜訊話題、文章全文。每次請求都即時讀取。
